## 二、★★★ 阶段一核心产出：推翻 H94「本底崩溃」结论

### 2.1 H94 的原始推理（及其漏洞）

H94 统计 `history.log` 得 1172 次 panic，9/28 起每天 50–380 次，
⇒ 结论「**设备本底极不稳定，panic 不能归因于开火**」。

**H94 的漏洞**：它只看了「量」，**没做时间分布显著性检验**。

### 2.2 本轮重算（同日对比，排除量级干扰）

| 日期 | AP_S_PANIC | 本项目状态 |
|---|---|---|
| 08-02 | 1 | 未开工 |
| 09-27 | 1 | 未开工 |
| 09-28 | 53 | 未开工 |
| 09-29 | 24 | 未开工 |
| 09-30 | 88 | 未开工 |
| 10-01 | 128 | 未开工 |
| 10-02 | 378 | 未开工 |
| 10-03 | 235 | 未开工 |
| 10-04 | 108 | **H88/H90 开火** |
| **10-05** | **3** | **H97(08:52:50) / H98(09:04:45) 开火** |

### 2.3 ★★ 10-05 当日的决定性分布

```
10-05 全天 AP_S_PANIC = 3 条：
  08:52:27   ← H97 开火前 23 秒
  08:57:59   ← H97 开火窗口内（窗口 08:52:50–08:57:59）
  09:07:32   ← H98 开火窗口内（窗口 09:04:45–09:07:32）
```

**我们的开火窗口合计 8 分钟 = 全天 0.56%，却容纳了 2/3 的 panic。**

假设 panic 随机分布（与本项目无关）：
```
P = C(3,2) × (8/1440)² × (1 − 8/1440) ≈ 6 × 10⁻⁵
```
**⇒ 拒绝「与本底无关」的原假设，p ≈ 6e-5。**

### 2.4 修正后的结论

| 原结论（H94） | 本轮修正 |
|---|---|
| 设备本底不稳定，panic 无法归因 | **量级高但时间上强相关于开火** ⇒ 可归因 |
| 「enforcing=1 不能证明写没生效」 | 该条**仍成立**（跨重启判据失效） |
| 每天 50–380 次 ⇒ 不能归因 | **错误**：10-05 是本项目造成的集中 |

**⇒ 开火与 panic 存在因果关联，本项目不是「无辜的」。**

## 三、★★★ 阶段二：stage0 DELETE 窗口是崩溃定位点

### 3.1 两轮崩溃位置完全一致

| 轮次 | 完成 attempt | 崩溃位置 |
|---|---|---|
| H97 | 107 | `DELETE_ROLE_GATE_PASS` 之后 |
| H98 | 51 | `DELETE_ROLE_GATE_PASS` 之后 |

**存活数 107 vs 51 ⇒ 概率性触发，非固定计数器。**

### 3.2 崩溃窗口精确定位（源码级）

`f77.c:1461` `DELETE_ROLE_GATE_PASS` → `f77.c:1510` `EXEC_REPEAT_GATE_PASS` 之间。

```c
/* f77.c:1472-1481 */
atomic_store_explicit(&prime.start, 1, memory_order_release);
atomic_store_explicit(&shared->delete_go_ns, begin_ns, memory_order_relaxed);
atomic_store_explicit(&shared->delete_go, 1, memory_order_release);
for (int i = 0; i < nworkers; i++)
    join_or_preserve(workers[i], "delete");     /* ← 56000 timer 并发删除 */
```

⇒ **崩溃发生在「56000 个 hrtimer 的并发批量删除」期间。**

### 3.3 H88「零 panic」对照实验的可靠性复核

HANDOFF §2.7.3 声称「H88 开火 22:43:30 → 零 panic ⇒ H88 无害」。

**本轮复核：该结论证据不足，且真实原因已找到。**

- `h88_run_20261004_224330.log` 仅 **286 B**，内容止于「✓ 三重校验通过」，
  **没有「单发结束」行**（对比 H90 日志有该行）。
- 无 H88 的设备侧日志（`h88*_dev.log` 不存在）。

### 3.4 ★★★ H88 真因：卡在 `hold_corrupted_state()` 死循环

`f77.c:7973-7984` 的注释**直接给出了答案**：

```c
/*★★★★★★★★★★ H90：selinux 直打模式【禁止保态死循环】(MEY_SELINUX_TARGET_NOHOLD)
 * hold_corrupted_state() 是为 W1 桥接路径设计的（misc_list 被改坏，需停在原地
 * 等人工救援，避免继续跑把设备写得更坏）。
 * 但 selinux 直打模式：
 *   ...
 *   - 停在这里会把主机侧单发脚本挂住 30 分钟（H88 实测）
 * ⇒ 干净退出，交主机侧独立通道判据 */
```

`hold_corrupted_state()`（`f77.c:2618`）→ `hold_cred_unknown()`，是 `noreturn` 死循环。

**⇒ H88 的真相**：
1. H88 跑的是 **W1 桥接路径**（那时 `SELINUX_TARGET_NOHOLD` 还没加，见 `f77.c:7973` 注释
   「H90：…禁止保态死循环」⇒ 说明该开关是 **H90 才引入的**）。
2. H88 进 stageB 后桥没开 ⇒ 走到 `hold_corrupted_state()` ⇒ **死循环挂住**。
3. 主机侧脚本等 30 分钟后超时放弃 ⇒ 日志缺「单发结束」行。
4. 「设备继续在线 33 分钟」= 设备**正常，只是 exploit 卡在死循环里**。

**⇒ 「H88 零 panic ⇒ 写原语无害」这个推论不成立。**
H88 的 exploit **根本没跑完**，它既没验证「有害」也没验证「无害」。
这不是「零 panic 的对照」，而是「**未完成的实验**」。

### 5.2 ★★★ 崩溃机制新假设（H100-A）

**观察**：前 51（H98）/ 107（H97）个 attempt **完美执行**，然后突然崩溃。

`LANE_DONE` 数据（两轮末次）：

| 轮次 | deleted | errors | delete_us | exec_overlap |
|---|---|---|---|---|
| H97 seq=107 | 56000 | 0 | 28,954 | 1 |
| H98 seq=51 | 56000 | 0 | 29,756 | 1 |

⇒ **stage0 每轮都正确完成，崩溃是累积后突发。**

**H100-A 假设**：
> stage0 每个 attempt 会对内核状态造成**不可逆的微小污染**（`STAGE0_DIRTY_ARM` 每轮都打印，
> 见 `f77.c:2971` `atomic_store(&kernel_state_dirty, 1)`），累积到某个阈值后崩溃。

**判别实验（下一轮）**：

| 实验 | 参数 | 预期 |
|---|---|---|
| E1 | `stage0=51`（刚好卡在 H98 崩溃点前，不执行 stageB） | 不崩 ⇒ 支持累积假说 |
| E2 | `stage0=107`（H97 崩溃点） | 崩 ⇒ 复现 |
| E3 | `stage0=51` × 连续两次（同 boot） | 第二次崩 ⇒ 累积性铁证 |

**E1 最有价值**：若 `stage0=51` 且 `SELINUX_TARGET=0` 完整跑完不崩，
则证明**崩溃与 stage0 的累积量相关**，而非某个固定逻辑。
