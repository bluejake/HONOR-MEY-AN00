## 三、★★★ 核心判定一：M-A 被强烈证伪

### 3.1 似然计算（Python 复核，铁律①）

```
M-A 参数（由 H97/H98/R2 的崩溃 attempt 定出）：
    q = 0.015306   ⇒ 均值崩溃 attempt = 65.3

★ 在 M-A 成立的前提下，观测到「200 attempt 不崩」的概率：
    (1-q)^200 = (1-0.015306)^200 = 0.045736 = 4.57%
```

**⇒ 若 M-A 成立，R3 不崩的概率仅 4.57%（小概率事件）。**

### 3.2 对比 M-B

```
M-B 参数（由 H97/H98 的存活墙钟定出）：
    λ = 0.004202 /s   ⇒ 均值存活 238.0 s

★ 在 M-B 成立的前提下，观测到「301 s 不崩」的概率：
    exp(-λ·301) = exp(-0.004202×301) = 0.2823 = 28.23%
```

**⇒ M-B 完全容纳 R3 的结果（28.23% 属常见）；M-A 不容纳（4.57%）。**

### 3.3 判别力对比

| 模型 | R3 观测的似然 | 判定 |
|---|---|---|
| **M-A**（按 attempt 崩） | **4.57%** | ❌ **强烈证伪** |
| **M-B**（按时间崩） | **28.23%** | ⚠️ **未排除** |

**似然比 = 28.23% / 4.57% = 6.18×** ⇒ 单这一发就为 M-B 提供 **6.2 倍**的相对支持。

### 3.4 ★★ 与 H102 判定的关系（必须显式说明）

H102 §6.2 曾判「倾向 M-A（BF=21.64）」。**该判定基于 3 个样本（H97/H98/R2），本轮加入 R3 后方向翻转。**

| 阶段 | 样本 | BF(M-A/M-B) | 判定 |
|---|---|---|---|
| H102（n=3） | H97/H98/R2 | 21.64 | 倾向 M-A |
| **H103（n=4）** | +R3 | **0.837** | **两模型近似等权，但 M-A 被 R3 单点强烈压低** |

**★ 结论表述（严谨版）**：
- **M-A 不再可信**（R3 的 4.57% 似然是硬反证）
- **M-B 仍未被排除**（28.23% 是常见事件）
- **但因 n=4 且 M-B 的 λ 由 H97/H98 两点定出（自证风险），仍不宜宣称 M-B 已确证**

## 四、★★★ 核心判定二：崩溃与 `pipe_count` 强相关（新事实）

### 4.1 四样本对照

| 样本 | `pipe_count` | 结果 | 崩溃 attempt | 墙钟 (s) |
|---|---|---|---|---|
| H97 | 6000 | 崩溃 | 108 | 309.0 |
| H98 | 6000 | 崩溃 | 52 | 167.0 |
| R2 | **500** | 崩溃 | **36** | **66.0** |
| **R3** | **8000** | ★ **未崩（跑满）** | — | 301.0（无崩溃） |

### 4.2 关键推论

**R2 与 R3 是「同业最强对照」**：
- 同一二进制（`f77_h102_20261005_095627`）
- 同一 `MEY_STAGE0_ONLY=1`
- 同一 `SELINUX_TARGET=0`
- 同一 `timer_goal=56000` / `MEY_ROLE_OVERRIDE` / `FAKE_ORDER1` 参数
- **唯一差异：`pipe_count` 500 vs 8000**
- **且两者 stage0 都全 MISS、都未进 stageB**

⇒ **崩溃的差异只能归因于 `pipe_count`。**

⇒ **★★ M-C2 的方向获得支持**：`pipe_count` 影响崩溃时机（`pc` 小 ⇒ 早崩；`pc` 大 ⇒ 不崩）。

### 4.3 与「stageB 致崩」假说的关系

| 假说 | R2 证据 | R3 证据 | 判定 |
|---|---|---|---|
| 崩溃由 stageB 引起 | 未进 stageB 却崩 | 未进 stageB 且不崩 | ❌ **不一致，证伪** |
| 崩溃由 stage0 的 `pipe_count` 相关路径引起 | `pc=500` → 36 崩 | `pc=8000` → 不崩 | ✅ **一致** |

⇒ **崩溃发生在 stage0 内部、与 `pipe_count` 相关的路径上**（`prepare_spray_pairs` 的 socketpair / `run_spray_phase` 的 pwrite+punch / `close_spray_pairs` 的 close）。

## 五、本章必须承认的实验缺陷（诚实记账）

### 5.1 `MEY_STAGE0_MAX_ATTEMPTS=200` 偏低

R3 跑满 200 即退出（301 s）。**若崩溃点在 attempt 205 或 350 s 处，本发观测不到。**

**为什么仍可判定 M-A 已证伪**：M-A 预测的崩溃中位数是 **65.3 attempt**，其 99.7% 分位为 `ln(0.003)/ln(1-q) ≈ 379` attempt。跑到 200 **已越过中位数的 3 倍**，4.57% 的似然足以构成强反证。

**为什么 M-B 需要延长验证**：M-B 的均值存活 238 s，R3 只跑到 301 s（1.26 个均值时间）。**须延长到 ≥600 s（2.5 个均值时间）才能给 M-B 强支持。**

### 5.2 H97/H98 与 R2/R3 的配置差异（混杂变量）

H97/H98 **未启用** `MEY_STAGE0_ONLY`（该开关是 H102 新增），且带 `SELINUX_TARGET=1`。

⇒ 严格来说 H97/H98 与 R2/R3 **不是同构实验**。但**不影响本轮结论**：
- H97/H98 与 R2/R3 在 stage0 路径上的每 attempt 动作相同（都全 MISS）
- 唯一差异在 stage0 之后的路径（H97/H98 会进 stageB；R2/R3 因全 MISS 也不会进）
- **R2 vs R3 是严格同构对照**，已足以支撑「崩溃与 pipe_count 相关」的结论

## 八、★ 环境坑（本轮新增，写入纪律）

**`nohup bash script.sh > out.txt 2>&1 &` 在本机 Git Bash 下不生效**：
- 症状：`console.txt` 为 0 字节、脚本未推进（设备侧无 push 产物）、`ps` 无对应进程
- 诊断：前台跑同样脚本，前 3 步（等设备 / boot_id / history.log）**全部正常**
- 结论：**adb 长脚本必须前台执行**（配 `timeout` 或 Bash 工具的长超时）。后台方式仅对 scrcpy 这类 GUI 进程有效。
