## 1. CVE-2026-43284（DirtyFrag）—— 已实测 root

### 1.1 实机证据（本轮采集）

| # | 证据 | 值 |
|---|---|---|
| E1 | `su -c id` | **`uid=0(root) gid=0(root) context=u:r:ksu:s0`** ✅ |
| E2 | `cat /proc/modules` | **`kernelsu 167936 4 - Live`**（★ 动态装载模块，非编入 Image） |
| E3 | `cat /proc/sys/kernel/random/boot_id` | `ff1bf964-3f8c-4597-bd9d-c4f0cbba618d` |
| E4 | `ls /data/adb/ksud` | 4,912,656 B，**时间戳 2026-10-08 12:20**（DirtyFrag UMH 链刚落地） |
| E5 | DirtyFrag 仓库 git commit | `70194ac`（2026-10-08 12:40）*"known-good baseline: **root VERIFIED on boot ff1bf964** (v6 UMH chain)"* |
| E6 | `getenforce` | `Enforcing`（Permissive 仅存在于漏洞窗口期，与 commit 描述一致） |

★ **E3 与 E5 的 `ff1bf964` 精确吻合** ⇒ 当前设备状态就是那次已验证的 root 运行的结果。

### 1.2 完整链（README + h212 已核实）

```
IpSecManager 建 AES-CBC/HMAC-SHA256 ESP transport（127.0.0.1）
  → splice(file)→pipe→vmsplice(hdr+ICV)→splice(pipe→UDP encap sock)
  → 内核 ESP input 原地解密 ⇒ 16B 对齐页缓存任意写（无写权限、无 COW）
  → patch#1: splicehelper 覆盖 crash_dump64（取得 crash_dump 域）
  → patch#2: 经 crash_dump 桥把 dirtyfrag.ko 写进 vendor_file 标签文件
  → hook /system/lib64/libc++.so 的 ostream::sentry
  → createOrphanProcess 双 fork ⇒ 孤儿被 init 收割 ⇒ init(uid=0,tid=1) 走 hook
  → shellcode: 写 u:r:vendor_modprobe:s0 → exec insmod <ko>
  → KO init: selinux_state=false（★ 全局 Permissive）→ call_usermodehelper 起 ksud
  → ksud 装载 kernelsu.ko LKM ⇒ su 可用
```

### 1.3 成功判据（全部满足）

| 判据 | 结果 |
|---|---|
| `id -u` == 0 | ✅ `uid=0(root)` |
| `getenforce` != Enforcing | ✅ 窗口期 Permissive（KO 写 `selinux_state=false`） |
| 一次受保护写 | ✅ `/data/adb/ksud` 已写入（root-only 目录） |

### 1.4 ★ 性质：**易失（ephemeral）root**

- `kernelsu` 是 **Live 模块**（`/proc/modules`），**不是**编入内核 ⇒ **重启即失效**，需每次重新执行
- 这与设备 **BL 锁定**（无法刷 boot.img）完全自洽
- 仓库自带 `Start on Boot` / `Automatic soft reboot`（默认关）用于持久化

### 1.5 ★★ 修正上一轮（H251）的一处误判

H251 判定「root 来源 = KernelSU 刷入，与本项目 CVE 无关」——**此项判断错误**。

**正确结论**：KernelSU **不是刷入的**，而是 **DirtyFrag（CVE-2026-43284，本项目的工作）动态加载的 LKM**。

| 反证 | 说明 |
|---|---|
| BL 锁定 | 无法刷 boot/init_boot ⇒ 不存在"刷入"路径 |
| `kernelsu` 在 `/proc/modules` | 是**可卸载 LKM** 形态；若编入 Image 不会出现在此处 |
| 模块文件与工具资产同尺寸 | 工具内嵌 `kernelsu-android15-6.6.ko` = **316,224 B**，与仓库 assets `O101O` = 316,224 B **逐字节同尺寸** |
| `/data/adb/ksud` 时间戳 = 今天 12:20 | 由 DirtyFrag UMH 链（`call_usermodehelper`）刚投放 |

⇒ **设备当前的 root 就是本项目 CVE 链（DirtyFrag）的成果**，KernelSU 只是该链末端的 root 提供者（DirtyFrag 的设计就是"以 KernelSU 为载荷"）。

## 2. CVE-2026-49881（Telecom）—— 不能 root

### 2.1 漏洞性质（外部情报）

| 项 | 值 |
|---|---|
| 模块 | `packages/services/Telecomm`（Android **17**） |
| 触发点 | `InCallController.serviceClassExists()` |
| 类型 | **userspace Java 逻辑漏洞**（非内存破坏、非内核） |
| 效果 | 攻击者 app 的代码在 **`system_server`** 中执行（**UID 1000**，非 0） |
| 链路 | `TelecomManager.addCall()` → `getInCallServiceComponents()` → `createPackageContextAsUser(...)` 用 `CONTEXT_INCLUDE_CODE\|CONTEXT_IGNORE_SECURITY` → `getClassLoader()` → 触发攻击者 `AppComponentFactory` 静态初始化 |
| 权限 | `MANAGE_OWN_CALLS`（normal，安装即授予，无弹窗） |
| 修复 | 2026-09 公告 |

### 2.2 ★ 官方自述：**它不是 root 链**

来源 `JingMatrix/pixel-ksu-root:cves/cve-2026-49881-telecom/README.md` 原文（**非本项目推断**）：

> "It is not a memory-corruption bug and not a kernel bug; it is a **privilege-domain pivot**, and **on its own it roots nothing**."

> "What it is not: it holds **neither general system administration nor module loading**, so by itself it **loads no module and disables no policy**, and it **runs no native code**. It is a **pivot** that changes which kernel bugs are in range, **not a root chain**."

⇒ 它只能到 **system_server (uid 1000)**，**不能**变成 uid 0，也**不能**加载模块或关 SELinux。

### 2.3 ★★ 本机存在性核查（本轮实测，**结论：大概率不存在**）

方法：从设备拉取 `Telecom.apk`（6,608,623 B，`/system/priv-app/Telecom/`），用 androguard 反编译 dex。

| # | 检查项 | 结果 | 判定 |
|---|---|---|---|
| C1 | `InCallController` 类 | 存在，**186 个方法** | — |
| C2 | **`serviceClassExists` 方法** | **不存在** | ☠️ 漏洞触发点缺失 |
| C3 | 全 dex `Class.forName` | 31 处，**Telecom 包内 0 处** | ☠️ 无类加载 |
| C4 | `createPackageContextAsUser` 调用点 | 6 处（Ringer / RingtoneFactory / TelecomSystem / TelephonyUtil / DisconnectedCallNotifier / MissedCallNotifierImpl） | — |
| C5 | **上述 6 处的 flags 实参** | **全部为 `0`** | ☠️ 无 `CONTEXT_INCLUDE_CODE\|CONTEXT_IGNORE_SECURITY`(=3) |
| C6 | 上述 6 处的包名来源 | 全部 `getPackageName()`（**自身包**） | ☠️ 不接受攻击者包名 |

★★ **三重否决**：
1. 漏洞方法 `serviceClassExists` 不存在
2. Telecom 包内**完全没有** `Class.forName`
3. 所有 `createPackageContextAsUser` 均传 flags=0（漏洞要求 3）

⇒ **该漏洞在本机 Telecom 上不可触发。**

**原因推断**（标注 `[未完全确证]`）：漏洞标注影响 **Android 17**，而本机是 **Android 16**；`serviceClassExists` 这一"元数据驱动 + 类存在性检查"逻辑很可能是 **Android 17 引入**的，Android 16 的 Telecom 无此代码。因此本机**既不是"已修复"也不是"存在但未修"，而是"从未有过"**。

## 3. 战略价值对比（供后续决策）

| 维度 | 43284 DirtyFrag | 49881 Telecom |
|---|---|---|
| 终点权限 | **uid 0**（含 SELinux Permissive） | uid 1000（system_server） |
| 需内核漏洞 | 是（ESP/AES-CBC，本机 sink 未修） | 否（纯 Java） |
| 需竞态 | ❌ 无（确定性逻辑漏洞） | ❌ 无（逻辑漏洞） |

★ 注意：49881 的**潜在价值**在于「域扩大」——`R0` 报告里 43499/64560 的多个卡点（`perf_event_open`、`kprobe_events`、`bpf()`、`io_uring_setup` 全 EACCES）本质是 **shell 域 (u:r:shell:s0) 的 SELinux/LSM 限制**，system_server 域权限更高。**但本机缺这段代码，此路不通**。

## 4. 结论与建议

1. **43284 这一条已经打完**——设备现在是 root 状态，链路、判据、产物齐全，仓库有 `releases/honor-root-tool-root-verified-ff1bf964.apk` 作为回滚锚点。
   - 待办（仓库 commit 自述的已知问题）：`[I]` 先于 `[D]` 导致 ksud UAPI mismatch、`ksud late-load` 完成后恢复 Enforcing 使 UMH 子进程失去 silent-dontaudit、`asset_names.c` 未同步 v7。
2. **49881 不能 root，且本机不存在**——应从候选表移除（至少对本机 Android 16）。
3. **对 43499 的影响**：49881 这条"域扩大"的辅助路径在本机不可用 ⇒ **43499 仍只能在 shell 域内求解**，`h251` 方案里的阶段 1–3 不受影响。
4. **如需 49881 级别的域扩大**，需另找本机实际存在的 userspace pivot（`R5` 的 `hdbd` 与 `kcmdline_prop` 是两条未裁决的活线）。
