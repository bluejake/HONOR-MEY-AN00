## 3 死因定论（设备端残留铁证）

设备实测（本次）：

```
$ adb shell cat /data/local/tmp/mp.proof
argv0=./mp.sh args=
u:r:shell:s0  CapPrm:	0000000000000000
CapEff:	0000000000000000
CapBnd:	00000000008000c0
```

**`mp.sh` 确实被内核以 usermode helper 身份**跑起来了\*\*（有 `argv0=./mp.sh` 记录，且 `modprobe_path` 当时确实指向它），  
但该 helper 进程的实测身份是：

| 项         | 值                  | 应有值（root 成功时）              |
| --------- | ------------------ | -------------------------- |
| SELinux 域 | **`u:r:shell:s0`** | `u:r:kernel:s0` 或至少 `su` 域 |
| `CapPrm`  | **0**              | 非 0（全 cap）                 |
| `CapEff`  | **0**              | 非 0                        |
| `CapBnd`  | `0x8000c0`         | 同上                         |

⇒ **`errno=10` / `STAGE8_ROOT_FAIL` 的真因：modprobe helper 继承了发起者的 SELinux 域（shell）与零 capability**  
⇒ helper 自身没有能力做任何提权动作，`mp.sh` 拿到的是 uid=2000 shell 身份。

**同 boot 内 `enforcing=1`（见 `STAGE8_ENV_GATE_PASS` 行）** ⇒ 这是**同一 boot 内的直接观测**，  
不受「跨重启归因失效」影响，可作为有效判据。

⇒ **瓶颈精确收敛到「SELinux 域继承」这一个点**，而不是「桥打不开」「写原语不行」「找不到 cred」。

## 7 下轮第一步（建议）

**方向切换：回到 stage8 触发环节，集中打「helper 的 SELinux 域」这一个点。**

候选路线（按优先级）：

1. **同 boot 内先把 `selinux_state.enforcing` 写 0（permissive）再触发**  
   —— 当前 `STAGE8_ENV_GATE_PASS` 显示 `enforcing=1` 时就直接触发，等于自缚。  
   本链已有任意写 ⇒ 写 `enforcing=0` 是同一原语的一发。**这也是 H90 的原设计，但当时卡在桥不开；现在桥已开。**
2. **改 `modprobe_path` 前先改 `selinux_state`**，或改用 `/proc/sys/kernel/core_pattern`（同样受域限制，需评估）。
3. **换 helper 载体**：`modprobe` 走 `call_usermodehelper` 时域由 `kernel_init`/`kthreadd` 决定，  
   通常应是 `u:r:kernel:s0`；本机实测为 `u:r:shell:s0` ⇒ **说明该 helper 不是走常规 `call_usermodehelper` 路径**，  
   或本机 SELinux 策略把 `modprobe` 域映射到了 shell。**这一条需要源码+策略双证，是新的主线问题。**

⚠️ 一 boot 一发；改 `modprobe_path` 属破坏性写，须在同 boot 内完成触发与判据读取。
