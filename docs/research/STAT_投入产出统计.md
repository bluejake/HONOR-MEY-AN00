## ⚠️ 零、先纠正前提：**两条主线 CVE 都还没拿到 root**

用户问「才得到的 root」，但实测数据显示：

| 路线 | 判据 | 实测结果 |
|---|---|---|
| **CVE-2026-64560**（`rb_erase` 写原语 → misc 桥 → stage8） | `STAGE8_ROOT_PASS` | **0 次命中**（全库 grep） |
| | `STAGE8_ROOT_FAIL result=-1 errno=10` | 6 次（ECHILD） |
| | 历史总账 | 桥打开过极多次（`MISC_BRIDGE_READ_PASS` 43 个日志 / `OPEN_PASS` 30 / `RW_PASS` 26），`STAGE8_ENV_GATE_PASS` 26 次，**但从未 root** |
| **CVE-2026-43499**（rt_mutex PI） | 写原语落地 | **从未观测到**。H248 定论：`fire-after-EDEADLK` 是结构性失败点——画布就位与 `remove_waiter` 被调用**无法在同一线程/同一栈槽共存** |
| **CVE-2026-43284 DirtyFrag** | `id -u`=0 / `getenforce` / 受保护写 | ✅ **三判据绿**（boot `95f49e33`） |

★ **关键区分**（H250 已明确记录）：设备上现在能用的 `su` **来自 KernelSU**，是 DirtyFrag 链路注入 KO 后由 KernelSU 提供的，**与本项目研究的 64560/43499 CVE 链无关**：

```
dmesg: [15206:sh]KernelSU: newfstatat su->ksud!   ← KernelSU 在 execve 路径上
grep '43499|64560|rt_mutex|pi_blocked' dmesg  →  0 命中   ← 无本项目 CVE 痕迹
```

⇒ **所以「得到的 root」这个说法需要拆开看**：
- ✅ 确实拿到过 root —— 走的是 **DirtyFrag（CVE-2026-43284）** 路线
- ❌ 纯 CVE 研究目标（64560 / 43499 写原语）—— **仍未达成**

下面统计的是**整个项目的总投入**（含失败路线），因为这才反映真实成本。

## 十、这笔投入的性价比自评

### 赚到的

1. **3 项可复用的硬结论**（漏洞态判定 + kstack 随机化实证 + 64560 漏洞态）—— 这些是**资产**，换机/换版本可直接复用
2. **1 次真 root**（DirtyFrag 路线，含 APK 交付能力）
3. **完整的方法论体系**：一 boot 一发 / 独立透镜 / 写原语枚举全写点 / 0 命中必做阳性对照 / 画布偏移公式 / 消费器 frame 不重叠约束
4. **`/proc/bootconfig` 离线绕过**（Image 内嵌 gzip）
5. **对 64560/43499 的机制性判死**（省下未来重复投入）

### 亏的

1. **64560 的 stageB W1 投入产出比极差** —— 190 万次 MISS 换零结果。若早知「同一 exploit 在同代 GKI 上过（opace6）」但**它同样卡在 W1 参数标定**，本可以更早转向 DirtyFrag
2. **102 GB 磁盘** —— 主要是固件提取物，事先没规划分层
3. **两棵源码树的版本核验走了弯路** —— `google_kernel_GKI-6.6.118` 被当作依据用了很久，最终证明是伪装树。**正确方法（blob 哈希比对）应在第一次使用前就执行**

### 如果重来，关键决策点应提前

| 决策点 | 实际 | 应有 |
|---|---|---|
| 源码树可信度 | 用了几轮才核验 | **第一次读之前**就 blob 比对 |
| 主线选择 | 64560 死磕 190 万次 | 先算「单次成功 boot 数」再决定投入 |
| 消费器 frame 冲突 | 7 发 panic 后才发现 | **画布布局定下来时就算 frame 区间** |
| 「不崩」判据 | 5 发零 panic 才发现是早退假象 | 铁律㊲：**「不崩」≠「写成功」**（这条应前置） |
