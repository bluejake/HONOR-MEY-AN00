## 1. 两个 CVE 的技术本质

### 1.1 CVE-2026-43499（GhostLock / IonStack）

**类型**：CWE-416 UAF（不是越界、不是类型混淆）

**机理**（`kernel/locking/rtmutex.c`）：
PI-futex 代理锁回滚路径上，`remove_waiter(lock, waiter)` 在清理挂起状态时**操作 `current` 而不是 `waiter->task`**：

```c
// 6.6.118 实测原文（未修补）
raw_spin_lock(&current->pi_lock);
rt_mutex_dequeue(lock, waiter);
current->pi_blocked_on = NULL;      // ← 应为 waiter->task->pi_blocked_on
raw_spin_unlock(&current->pi_lock);
```

- 自阻塞路径（`rt_mutex_slowlock` / `rt_mutex_finish_proxy_lock`）：`waiter->task == current`，行为不变。
- 代理路径（`rt_mutex_start_proxy_lock`，由 `futex_requeue()` 在 `FUTEX_CMP_REQUEUE_PI` 死锁回滚时**代替另一个 task** 调用）：`waiter->task != current` ⇒ 真正的挂起者其 `pi_blocked_on` 仍指向**已释放内核栈帧**中的 `rt_mutex_waiter`。
- 用户态随即可让 `pi_blocked_on` 指向的 `rt_mutex_waiter` 内容被邻帧数据覆盖 ⇒ 伪造 waiter 状态 ⇒ 任意内核写。

**触发条件**：
1. 线程 A 对 futex `FUTEX_LOCK_PI` 持锁；
2. 线程 B 对**另一把** futex 做 `FUTEX_LOCK_PI` + `FUTEX_WAIT_REQUEUE_PI`（挂起在 A 的 pi 链上）；
3. 线程 C 用 `FUTEX_CMP_REQUEUE_PI` 制造 `EDEADLK` ⇒ 触发 `rt_mutex_start_proxy_lock` ⇒ 回滚 ⇒ `remove_waiter(current≠waiter->task)`。

**修复补丁**：
- 上游：`3bfdc63936dd4773109b7b8c280c0f3b5ae7d349`（把 `current` 换成局部 `task = waiter->task`，含 `rt_mutex_adjust_prio_chain(..., task)`）。
- 第三方 backport 实证：`refs/openvz-cve-patch-2026/CVE-2026-43499-vzkernel3.10.patch`（openVZ 3.10 backport，含完整注释说明该 bug 的代理路径成因）。

**6.6.118 上是否残留**：**残留，未修补**（证据见 §0 表；逐行代码见 §3.2）。

### 1.2 CVE-2026-64560（posix-cpu-timers 非 leader exec 竞争 UAF）

**类型**：CWE-416 UAF + 竞态；引入于 v5.7（`55e8c8eb2c7b`，"Store a reference to a pid not a task"）

**机理**：
`k_itimer` 缓存的是 **pid 引用**（`it.cpu.pid`），操作时 `pid_task()` 查找 + `lock_task_sighand()`。竞态窗口：

```
sys_timer_delete()                     exec()（由非 leader 线程发起）
  posix_cpu_timer_del()                  de_thread() → switch_leader()
  p = pid_task(pid, pid_type)   ← 旧 leader    release_task(old_leader)
  sighand = lock_task_sighand(p)            __exit_signal(old_leader)
    (p->sighand == NULL) → unlock, return 0     tsk->sighand = NULL
  free_posix_timer()   ← k_itimer 被释放      unhash_task(old_leader)
```

**关键点**：`exec()` 与 `exit()` 不同——exec 时 TGID 不变，挂在 `signal->cpu_timers` 上的 armed 定时器**被继承、仍入队** ⇒ `run_posix_cpu_timers()` 遍历 timerqueue 访问已释放对象 ⇒ UAF 读写。

**必要条件**（三者缺一不可）：
1. `CLOCK_PROCESS_CPUTIME_ID`（以 TGID 为目标，exec 后被继承；`CLOCK_THREAD_CPUTIME_ID` 不行）；
2. **非 leader 线程 exec**（`switch_leader()` 使旧 leader 随即 `sighand = NULL`）；
3. `timer_delete()` 恰与 `de_thread()/__exit_signal()` 竞争命中。

**修复补丁**（4 处，缺一不可）：
1. `__exit_signal()`：`tsk->sighand = NULL` → `smp_store_release(&tsk->sighand, NULL)`；
2. `lock_task_sighand()` 的 `!sighand` 路径加 `smp_acquire__after_ctrl_dep()`；
3. 新 helper `timer_lock_sighand()`：`sighand == NULL` 时**不返回而是重试查找**（exec ⇒ 查到新 leader；exit ⇒ 查找失败才放弃）；
4. `_del` / `_set` / `_rearm` 三函数统一改用该 helper。

主line `920f893f735e`；6.6 stable 修复版本 **6.6.147**（`12a891c773ae`）。设备 6.6.118 < 6.6.147 ⇒ 版本上即未含修复。

**6.6.118 上是否残留**：**残留，未修补**（源码证据见 §3.3）。

## 2. L2 复核：CVE-2026-43499 rt_mutex / pselect 跨帧滑动路线

### 2.1 H47 判「机制不成立」的两条依据 —— 逐条复核

#### 依据 A：「nfds ≥ 320 是否真走 kmalloc」→ **结论正确，但推导链断了**

H47 的论证是：任何能装下 14 词的 `nfds` 都会让内核走 `kmalloc` 堆 ⇒ `fd_set` 与内核栈不重叠 ⇒ 几何不成立。

**前半句正确，后半句的因果链是错的**。正确因果是：

- `fs/select.c` 的阈值不是「装下 14 词」，而是 **`size > sizeof(stack_fds)/6`**，其中 `stack_fds` 是 `long[SELECT_STACK_ALLOC/8] = long[32]` = **256 字节**。
- 阈值 = `256/6` = **42**（整数除法）。`size = 8 × words_per_set`，所以
  - `words_per_set ≤ 5`（`size ≤ 40 ≤ 42`）⇒ **栈**；
  - `words_per_set ≥ 6`（`size ≥ 48 > 42`）⇒ **kvmalloc 堆**。
- 参考实现默认 `PSELECT_ROUTE_NFDS 320` ⇒ `words_per_set = 5` ⇒ `size = 40` ⇒ **仍然走栈**。

**本机机器码交叉验证**（`core_sys_select @ 0xffffffc080243f6c`，capstone 实测）：

```asm
0xffffffc080243f6c  add  x8, x23, #0x3f
0xffffffc080243f70  lsr  x8, x8, #3
0xffffffc080243f74  and  x24, x8, #0x1ffffffffffffff8   ; x24 = size(字节)，向上对齐 8
0xffffffc080243f78  cmp  x24, #0x2b                    ; 0x2b = 43
0xffffffc080243f7c  b.hs #0xffffffc0802441cc            ; >= 43 → kvmalloc
```

`cmp #0x2b(43)` + `b.hs` 与源码 `size > 42` 语义**完全等价**（下一个 8 的倍数是 48）。机器码与源码一致，阈值判定无歧义。

⚠️ 注意 `and x24, ..., #0x1ffffffffffffff8` 这一步：`size` 被**向上**取整到 8 的倍数，不是截断。所以不存在「取整后反而变小从而留在栈上」的边界情况。

**所以 H47 的依据 A 属于「结论对、理由错」**：真正让 `nfds≥320` 落回堆的不是 320 这个数，而是「要让 `size > 42` 就必须 `nfds ≥ 321`」。

| `nfds` | `words_per_set` | `size` | 分配 | 3 张 bitmap 总可控字节 |
|---|---|---|---|---|
| 257–320 | 5 | 40 | **栈** | 120 B |
| 321–384 | 6 | 48 | 堆 | 144 B |
| 449–512 | 8 | 64 | 堆 | 192 B |

#### 依据 B：「跨帧滑动几何」→ **结论正确，但 H39 与 H47 都用错了偏移，且该几何在本机彻底不成立**

这是本轮**最实质的发现**。几何要求：用户经 `pselect6` 写入的三张 `fd_set` bitmap，恰好覆盖 `futex_wait_requeue_pi` 栈帧上那个 `rt_mutex_waiter`（`struct rt_mutex_waiter` = `0x70` = 112 字节 = **14 个 8 字节 word**）。

我用 capstone 独立重测了四个关键量（不采信 H39 的结论）：

| 符号 | vaddr | 实测序言 | H39 用的 | 差异 |
|---|---|---|---|---|
| `__arm64_sys_futex` | `0xffffffc080119ad8` | `paciasp; sub sp,#0x80` | 0x80 | ✔ 一致 |
| `futex_wait_requeue_pi` | `0xffffffc080958e1c` | `paciasp; sub sp,#0x1c0`，`x29=sp+0x160` | 0x1c0 | ✔ 一致 |
| `__arm64_sys_pselect6` | `0xffffffc080244230` | `paciasp; sub sp,#0x90` | 0x90 | ✔ 一致 |
| `core_sys_select` | `0xffffffc080243ee8` | `paciasp; sub sp,#0x1e0` | 0x1e0 | ✔ 一致 |

帧深一致 ⇒ **H39 的 SHIFT=19 结论并非帧深算错，而是「帧内偏移」取错了**。关键两处：

1. **`rt_waiter` 的真实偏移是 `sp+0x90`，不是 H39 用的 `sp+0xa8`。**
   实测（`futex_wait_requeue_pi`）：
   ```asm
   0xffffffc080958ea4  add  x0, sp, #0x90
   0xffffffc080958ea8  mov  w1, wzr
   0xffffffc080958eac  mov  w2, #0x70        ; ← 0x70 = sizeof(rt_mutex_waiter)，与源码一致
   0xffffffc080958eb0  add  x27, sp, #0x90
   0xffffffc080958eb4  bl   0xffffffc080552fc0   ; memset(waiter, 0, 0x70)
   ```
   H39 用的 `sp+0xa8`（来源是它自己写的 `x29-0xb8 = sp+0xa8`）**不是 waiter 基址**。
   ⇒ waiter = `T − (0x80 + 0x1c0) + 0x90` = **`T − 0x1B0`**（H39 算成 `T − 0x198`，**偏大 0x18**）

2. **`stack_fds` 的真实偏移是 `sp+0x70`，不是 H39 公式里的 `sp+0x40`。**
   实测（`core_sys_select`）：
   ```asm
   0xffffffc080243f28  add  x0, sp, #0x70
   0xffffffc080243f2c  mov  w2, #0x100       ; ← 0x100 = 256 = SELECT_STACK_ALLOC
   0xffffffc080243f3c  add  x19, sp, #0x70
   0xffffffc080243f40  bl   0xffffffc080552fc0   ; memset(stack_fds, 0, 256)
   ```
   `w2 = 0x100` 与 `SELECT_STACK_ALLOC = FRONTEND_STACK_ALLOC = 256` 精确吻合，**这从机器码独立确认了 `stack_fds` 就在 `sp+0x70`，且它就是那 256 字节的栈数组**。
   H39 公式用了 `- 0x40`（它正文 §3.2 明明写的是「`add x0, sp, #0x70`」，但 §3.3 代入公式时却写成 `0x40`）⇒ **H39 自身前后矛盾**。
   ⇒ stack_fds = `T − (0x90 + 0x1e0) + 0x70` = **`T − 0x200`**（H39 算成 `T − 0x230`，偏大 0x30）

**重算 SHIFT：**

```
waiter      = T − 0x1B0
stack_fds   = T − 0x200
waiter − stack_fds = 0x50 = 10 words   ⇒  SLIDE_PSELECT_WORD_SHIFT = 10
```

H39 报的是 **19**。差异来源：`(0x1B0−0x200)=0x50=10` vs H39 的 `0x230−0x198=0x98=19`，**两处偏移同时算错、误差方向叠加**。

**★ 致命的一步：把修正后的 SHIFT 代回 §2.1 依据 A 的阈值约束，本机几何彻底不成立。**

逻辑数组（read/write/exception 三张 bitmap 视作一个 `3 × words_per_set` 的连续 word 数组）要同时容纳：
- 前导 `SHIFT = 10` 个 word（落在 waiter 之前的用户数据）；
- waiter 本体 `14` 个 word。

⇒ 需要 `SHIFT + 14 = 24` 个 word
⇒ `3 × words_per_set ≥ 24` ⇒ `words_per_set ≥ 8` ⇒ **`nfds ≥ 449`**
⇒ `size = 8 × 8 = 64` 字节
⇒ **`64 > 42` ⇒ 必走 kvmalloc 堆**

**即：要让「14 词 waiter + 10 词前导」在同一个逻辑数组里对齐，`fd_set` 就必须被搬上堆；而堆地址与内核栈地址不重叠，跨帧滑动几何从根本上不可能成立。**

| SHIFT | 需覆盖 word | 最小 `words_per_set` | 对应最小 `nfds` | `size` | 分配位置 |
|---|---|---|---|---|---|
| 0 | 14 | 5 | 257 | 40 | 栈 ✔ |
| 1 | 15 | 5 | 257 | 40 | 栈 ✔ |
| 2 | 16 | 6 | 321 | 48 | **堆 ✘** |
| 3 | 17 | 6 | 321 | 48 | **堆 ✘** |
| 13（H39 上下文里的头文件值） | 27 | 9 | 513 | 72 | **堆 ✘** |
| **10（本机实测）** | **24** | **8** | **449** | **64** | **堆 ✘** |

**上表说明：只有 `SHIFT ≤ 1` 才可能落在栈上。** 而本机几何（`core_sys_select` 帧比 vanilla 深 `0x20`、`futex_wait_requeue_pi` 深 `0x10`）**必然把 SHIFT 顶到 10**，远超 1。

### 2.2 L2 终判：**死，且死因已定量钉死**

> **L2（CVE-2026-43499 rt_mutex / pselect 跨帧滑动）在本机 MEY-AN00 上彻底不可行。**
>
> **死因（三条独立、任一即致命）**：
> 1. **几何不成立（决定性）**：实测 SHIFT = 10（非常规的 0/1），而落栈要求 SHIFT ≤ 1。本机两处偏移都算错在「帧内偏移」而非「帧深」，导致上一轮误判为 SHIFT=13→19 并据此得出「可重启」。
> 2. **阈值不可绕过**：`fs/select.c` 阈值 42 字节是编译期常量（`SELECT_STACK_ALLOC=256`），用户无法影响。SHIFT=10 强制 `size ≥ 64 > 42` ⇒ 必上堆。
> 3. **目标对象不在堆**：即便强行上堆，`rt_mutex_waiter` 始终位于**内核栈**（`futex_wait_requeue_pi` 栈帧），堆/栈地址空间不重叠。
>
> **注意：死因与「2026-08 补丁」无关。** CVE-2026-43499 在 6.6.118 上**确实未修补**（§0/§3.2）。若换用**非 pselect 承载机制**（例如另找一个同样在栈上、且与 futex 栈帧有 `≤1` word 偏移差的用户可写缓冲区），漏洞本身仍可能被利用 —— 但那属于**全新变体**，不是 L2。

### 2.3 L2 的可证伪判据

| 判据 | 方法 | 预期（若 L2 仍活） | 预期（若已死，与本报告一致） |
|---|---|---|---|
| 承载机制分配位置 | 反汇编 `core_sys_select`，确认 `cmp #0x2b / b.hs` 之后 `stack_fds` 是否仍为 `sp+0x70` | `nfds≥449` 时 `bits` 变成 kvmalloc 返回值（≠ 栈地址） | ✔ 已实测：`size≥48` 即跳 `0xffffffc0802441cc`（kvmalloc） |
| 几何 SHIFT | 反汇编 `futex_wait_requeue_pi`，找 `memset(sp+?, 0, 0x70)` 的 `add x0, sp, #?` | 应得 `SHIFT ≤ 1` | ✔ 已实测：`add x0, sp, #0x90` ⇒ SHIFT=10 |
| waiter 尺寸 | 读 `memset` 第三参数 | 应 ≠ 0x70 | ✔ 已实测 `mov w2, #0x70`，与 `sizeof(struct rt_mutex_waiter)` 吻合 |
| 运行时反证（**需上机，本轮未做**） | 令 `SLIDE_PSELECT_WORD_SHIFT=10`、`PSELECT_ROUTE_NFDS=449`，上机看 `slide pselect` 日志 | 出现 `SLIDE_OK` / 写原语生效 | `fd_set` 在堆 ⇒ 写落不到 waiter ⇒ 静默无效或 panic |

**上机判据（若将来要一次性彻底钉死 L2）**：把 `nfds=449` 与 `nfds=320` 各跑一组，比对 `SLIDE_*` 标记与是否 panic。预期 320 走栈但只覆盖 5/14 word（不足），449 覆盖 14/14 但在堆（无效）—— **两组都必然失败**。

### 5.2 静态分析：`honor_binder_alloc_do_copy_from_buffer`（capstone 实测）

```asm

0xffffffc08064b8e8  stp  x29, x30, [sp, #-0x50]!
0xffffffc08064b900  mov  x22, x0                  ; x22 = arg0
0xffffffc08064b908  cbz  x22, ...                  ; NULL 检查

0xffffffc08064b920  cbz  x4,  ...

0xffffffc08064b92c  mov  x26, #-0x100000000000000
```

**判读（谨慎，不下定论）**：
- 函数名含 `copy_from_buffer`，形态上**手工做用户地址翻译**（自行取页表项、合成线性地址），再调 `0xffffffc080552d90`（疑似 `memcpy`）。
- 有 4 个 NULL 检查、有页尾截断（`csel` 取 `min`）、有 `x19` 递减循环 ⇒ **表面上是有界的**，不是明显的长度溢出。
- ⚠️ 但**页表项来源可疑**：它从 `arg1+0x58` / `arg1+0x18` 取值来算偏移，而不是走标准 `copy_from_user` 的 `access_ok`。这种「自建地址翻译 + 手工拼接」的写法**天然容易出现 TOCTOU / 越界 / 页表项竞态**，且**完全绕过了内核统一的 user 内存访问审计**。
- **这是静态观感，不是已确认漏洞。** 见下方定级。

### 5.3 唯一调用点

| 项 | 内容 |
|---|---|
| **漏洞类型** | 厂商私有 binder 扩展中的**手工用户地址翻译**（疑似缺失标准 `copy_from_user` 语义） |
| **触发条件** | **未验证**。需要：① 到达该 binder 扩展的 ioctl 路径（**具体 ioctl 号未定位**）；② 通过 `sp+0xc8..0xcb` 的魔数检查；③ 构造能影响页表翻译的描述符字段 |

### 5.5 其余 5 个 proc 节点：`honor_binder_*_fops` 的槽位审计

解析 6 个 fops 结构（rodata，`struct file_operations` 标准槽序）：

| fops | vaddr | 非零槽位 |
|---|---|---|
| `honor_binder_transaction_proc_fops` | `0xffffffc081307010` | `+0x08 open`、`+0x10 release` |
| `honor_binder_state_fops` | `0xffffffc081307118` | 同上 |

| `honor_binder_failed_transaction_fops` | `0xffffffc081307538` | 同上 |

**判读**：6 个 fops **只有 `open` / `release`，没有 `read` / `write` / `ioctl`**。

## 9. 一句话总结

**两个 CVE 在本机 6.6.118 上都没被 2026-08 补丁修掉**——任务书「被覆盖的公开 CVE 一律排除」的前提不成立；
但 **L2 的 pselect 跨帧路线仍定量判死**（SHIFT=10 ⇒ 必走堆 ⇒ 堆栈不重叠），死因是机制性而非补丁；
**唯一新增可实证攻击面**是荣耀私有 `honor_binder_alloc_do_copy_from_buffer` 的手工页表翻译（未验证，优先级中）；
**L1 / CVE-2026-64560 方向不变**，仍是项目唯一主线。
