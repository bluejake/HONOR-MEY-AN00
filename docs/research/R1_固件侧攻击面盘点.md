### 1.2 ★ B：`kcmdline_prop` + `kcmdlinectrl` = 唯一一条属性→argv 注入链 [已实测存在，neverallow 归属未定]

| 环节 | 证据 |
|---|---|
| 类型 | `(type kcmdline_prop)` — `plat_sepolicy.cil` L4694 |
| **shell 可 set** | **`(allow shell kcmdline_prop (property_service (set)))`** — `plat_sepolicy.cil` **L27078** |
| kcmdlinectrl 域可 set | `(allow kcmdlinectrl kcmdline_prop (property_service (set)))` — L21907 |
| **argv 展开** | `risk_system/system_etc_init_kcmdlinectrl.rc` L20-22（原文） |

```rc
on property:kcmdline.binder=*
  wait_for_prop kcmdline.loaded 1
  exec -- /system/bin/kcmdlinectrl store binder ${kcmdline.binder:-c}
```

**这是全量 rc 扫描中唯一一处「属性值 → init `exec` 的 argv」构造**（共 32 条 `property_service set` 中只有这条对上了 argv）。init 会把 `${kcmdline.binder}` 原样展开为 `exec` 的第 4 个参数。

⚠️ **两个必须先解决的疑点**：

1. **neverallow 冲突**：`plat_sepolicy.cil` L25601 有 `(neverallow base_typeattr_880 kcmdline_prop (property_service (set)))`。CIL 的 `base_typeattr_880` 是某个属性属性集 —— **shell 是否在 880 内，决定这条 allow 是生效还是被 neverallow 压掉**。同组还有 L25595(arm64_memtag) / L25596(gwp_asan)，而 `permissive_mte_prop` / `kcmdline_prop` **没有** L255xx 系列的这一条。
2. **`kcmdlinectrl` 自身的域与运行用户未知**：rc 里是 `exec --`（无用户指定 ⇒ 继承 init 上下文）。且该二进制未被提取。

| 评级 | 前置条件 | 可证伪判据 |
|---|---|---|
| **中高**（唯一有完整证据链的 argv 注入候选） | ① `setprop kcmdline.binder X` 返回 0（验证 allow 胜过 neverallow）② `/system/bin/kcmdlinectrl` 对 `argv[3]` 不做二次分词、不当文件名用 | `setprop kcmdline.binder 'A A'` → `ps -AZ \| grep kcmdlinectrl` 看 argv 展开与域；若 setprop 返回 `Permission denied` 则**当场否证** |

**必做后续**：RE `/system/bin/kcmdlinectrl`。若它对 `store binder <val>` 中的 `<val>` 做 `fopen`/路径拼接，则 shell → 任意文件写。

### 1.3 ★ C：`permissive_mte_prop` / `arm64_memtag_prop` / `gwp_asan_prop` —— shell 可写的缓解开关 [已实测存在]

| 证据 | 行号 |

语义：MTE（Memory Tagging Extension）运行时 permissive 模式开关。**`property_contexts` 未提取（缺口）⇒ 无法确定实际属性名。**

- 作为提权路径：**低**。MTE permissive / 关闭 memtag 只是削弱内存 tagging 检测，不直接给 root。

| 可证伪判据 |
|---|
| `getprop \| grep -i mte` 看设备上是否存在对应属性名；若存在，`setprop <name> 1; getprop <name>` 应返回 1。**若属性不存在或 setprop 报错 → 否证** |

### 1.4 ★ D：`shell` 可读 `/proc/modules`（模块情报）[已实测]

### 1.5 ★★★ E：`u:r:su:s0` 标签被实际使用，但 `su` 域规则处于未审状态 —— **本轮最大的审计盲区**

**发现 A（rc 侧，铁证）** `risk_system/system_etc_init_simpleperf.rc` 原文全文：

```rc
# Not a service because services can only be stopped with SIGKILL
# (or SIGTERM+200ms+SIGKILL with gentle_kill), and simpleperf
# needs more than 200ms to clean up.

on early-init && property:ro.boot.simpleperf.boot_record=*
  exec_background u:r:su:s0 root root -- /system/bin/simpleperf record -a -g --exclude-perf -o /tmp/boot_perf.data

on property:sys.boot_completed=1 && property:ro.boot.simpleperf.boot_record=*
  exec u:r:su:s0 root root -- /system/bin/killall simpleperf
```

**荣耀在自己的 init.rc 里显式使用 `u:r:su:s0`（`su` 是 Android 提权后的标准域标签）并以 `root root` 身份跑。** 这不是 AOSP 遗留 —— AOSP 自己的 simpleperf.rc 不用 seclabel 显式指定。

**发现 B（触发条件）** `ro.boot.simpleperf.boot_record` 来自 `ro.boot.*`（bootloader 注入），**用户/adb 不可写** ⇒ 正常启动**不触发**。但这条规则证明了 `su` 域**在本机策略中存在且可被 init 使用**。

**发现 C（致命疑点）** 在三个 cil 里**搜不到 `(type su)`**、也搜不到任何 `(allow ... su ...)`、`(typeattribute su)`。而 plat_sepolicy.cil 的 NUL 空洞（L36841–L53818）**恰好覆盖了 type 声明区**。

**结论：不能断言 `su` 域不存在，也不能断言其规则宽松。** 必须在二进制侧确认。

| 评级 | 前置条件 | 可证伪判据 |
|---|---|---|
| **未知-可能高**（必须先解 `su` 域规则） | 取得 `su` 域定义 | ① 静态：对 `sepolicy/precompiled_sepolicy`（2,016,860 B 二进制）跑 `sepolicy-analyze permissive` / 反编译，grep `type su` 与其 allow/neverallow；② 动态（需上机、另开任务）：`ls -Z /system/bin/simpleperf` 看 `su` 域是否可被 shell 触达、`getprop ro.boot.simpleperf.boot_record` 是否可由 `setprop` 影响（`ro.` 前缀应不可 ⇒ 直接否证触发路径） |

⚠️ **诚实的空白**：没有对 `precompiled_sepolicy` 做任何二进制分析（需要 `secilc`/`sepolicy-analyze`/libsepol 工具，当前案头环境不具备）。**上面 5 个 cil 文本文件之外的策略内容，本次一个字都没审。**

### 1.10 关于 `neverallow` 覆盖的诚实警告

- `system_ext_sepolicy.cil` 对 shell 只有 **2 条** neverallow（L4523 / L4527 `data_cota_para_file`）
- **`vendor_sepolicy.cil` 对 shell 的 neverallow 是 0 条**

这不是漏洞（AOSP 设计如此：vendor 策略在**构建期**由 `secilc` 校验 neverallow），但有一个实务后果：

> **编译期 neverallow 校验早已在荣耀固件构建时通过。这意味着任何 vendor 域的越界 allow 都不会在运行时暴露——静态审计无法发现它。** 换句话说，**不能把 neverallow 当作本项目的安全保证**，只能当作「已被构建期接受的现状」。

### 4.1 ★ kpatch.img 决定性结论 [已实测]

```
D:/MEY-AN00-root-repro/analysis/output/c_line/image/kpatch.img
size = 16,777,216
非零字节 = 0                    ← 逐字节扫描
非零 1MB 块 = 0 / 16            ← 独立复核
```

上一轮报告写「前 64 B 全 0」并标「⚠️ 待定」。**本轮确认整个分区 100.0000% 为零 ⇒ U2 彻底关闭，不再是「待定」。**

⚠️ **尺寸矛盾**（需澄清）：

| 来源 | kpatch 尺寸 |
|---|---|
| 固件包内 `image/kpatch.img` | **16,777,216 B = 16 MB** |
| GPT 分区 `kpatch_a` | **2.00 MB**（LBA 149,760–153,855） |
| GPT 分区 `patch_a` | **16.00 MB**（LBA 157,952–190,719） |

⇒ 16 MB 与 `patch_a` 吻合，却与 `kpatch_a`(2MB) 不符。**不影响 U2 结论（全零是独立事实）**，但若要重评 kpatch 必须先澄清。

### 4.2 eng_system / eng_vendor [已实测 header]

两者 header 逐字节相同，是 avbtool 1.3.0 生成的 SHA256-RSA2048 签名 vbmeta，内含 `AVB_DESCRIPTOR_TAG_PROPERTY`（`com.oem.base_version = "MEY-LGRP1-CHN 10.0.0.175"`）与 `sha256` 哈希描述符。

**为什么重要**：这两个分区是**工程版本（eng）的 vbmeta**，GPT 中各 3 MB / 1.5 MB 且 `attrs=0x1000000000000000`。量产机是否挂载 eng vbmeta、AVB 校验链是否包含它们，是一条独立的 AVB 信任链问题。但要利用需写块设备 ⇒ U2 悖论。**评级：低（当前不可达），记录在案。**
