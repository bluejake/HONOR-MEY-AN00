## 三项决定级裁决（R9，全汇编级）

### ① `remove_waiter` = 漏洞变体

`@0xffffffc081080e60`，size `0x26c`：

```asm
0xffffffc081080e98:  mrs      x20, sp_el0           ; ★ x20 = current（per-CPU）
0xffffffc081080e9c:  add      x21, x20, #0x90c      ; ★ &current->pi_lock
0xffffffc081080ea8:  bl       #0xffffffc081083358   ;   _raw_spin_lock
0xffffffc081080edc:  bl       #0xffffffc08003a9d4   ;   rb_erase（rt_mutex_dequeue 内联）
0xffffffc081080ee8:  str      xzr, [x20, #0x938]    ; ★★ current->pi_blocked_on = NULL
0xffffffc081080eec:  bl       #0xffffffc081083520   ;   _raw_spin_unlock
```

**决定性指纹**：清零写基址 `x20` 与锁基址 `x21 = x20 + 0x90c` **同源**。已修变体（6.6.139）写基址必须是从入参 `x1` 经 `#0x50` 链式 load 出的 `waiter->task`（另一个寄存器）。**本函数全 620 字节 `#0x50` 0 命中**（阳性对照：`rt_mutex_adjust_pi` 1 命中、`task_blocks_on_rt_mutex` 3 命中 ⇒ 正则有效）。

调用点 3 个，其中 `0xffffffc081080e58`（`rt_mutex_start_proxy_lock`）正是漏洞触发场景 —— 6.6.139 源码注释原文：*"When invoked from rt_mutex_start_proxy_lock() waiter::task != current !"*。

与 dc15 记录吻合（`1080e98: mrs x20, SP_EL0` + `1080ee8: str xzr,[x20,#0x938]`，dc15 记的是文件偏移）。

### ② ★ `CONFIG_RANDOMIZE_KSTACK_OFFSET=y` 且运行时生效

**smoking gun** —— `invoke_syscall@+0x8c`：

```asm
0xffffffc08004678c:  mrs      x8, tpidr_el1
0xffffffc080046794:  add      x9, x9, #0x80        ; &kstack_offset（精确匹配 0xffffffc082136080）
0xffffffc080046798:  ldr      w8, [x8, x9]         ; 读 per-cpu kstack_offset
0xffffffc0800467a0:  and      w8, w8, #0x3ff       ; 0..1023 页
0xffffffc0800467a8:  and      x8, x8, #0x7f0       ; 16B 对齐
0xffffffc0800467ac:  sub      x8, x9, x8           ; sp = sp - offset
0xffffffc0800467b0:  mov      sp, x8               ; ★★ 真的改 SP
```

**三重独立证据**：① Image 内嵌 bootconfig（`IKCFG_ST/ED` gzip，解压 212,910 B，头部自证 `Linux/arm64 6.6.118` + `CONFIG_LOCALVERSION="-4k"`）含 `CONFIG_RANDOMIZE_KSTACK_OFFSET=y`；② 符号 `early_randomize_kstack_offset` / `randomize_kstack_offset` / `kstack_offset` 齐备且 early_param 双分支完整；③ 上面的改 SP 代码。

**★ 副产品**：`/proc/bootconfig` 实测 EACCES 的封锁**已被离线绕过** —— bootconfig 就在 `Image-mey` 里。

**爆炸半径**：

| 路线类型 | 影响 |
|---|---|
| **固定栈偏移**（sigreturn ROP / 栈上变量硬编码 / MCAST 与 sigreturn 的栈几何） | ☠️ **全部作废** |
| **纯数据流**（UAF write 到任意内核地址 / 写堆上 `task_struct` 字段） | ✅ **不受影响** |

⇒ 43499 的利用原语是 `current->pi_blocked_on = NULL`（**写堆上 task_struct**）+ PI 链遍历，属「数据流」类 ⇒ **kstack 随机化不构成阻断**。但它解释了 dc15/chagall 为何栽在栈几何路线上。

### ③ CVE-2026-64560 漏洞态成立

| 树 | 版本 | `exit.c` 的 `sighand` 处置 | `timer_lock_sighand` |
|---|---|---|---|
| `kernel_nothing_sm8735` | 6.6.127 | **裸赋值**（line 209） | **0 命中** |
| `code-linaro-full` | 6.6.139 | **裸赋值**（line 209） | **0 命中** |

6.6.127 与 6.6.139 写法**字节级一致** ⇒ 补丁落地窗口下界推到 6.6.139 之后 ⇒ 本机 6.6.118 必然在漏洞侧。

**chagall「6.6.118 已修 43499」= 不可采信**：其 build 串 `ab158633 37`（高通通道）≠ 本机 `abogki518694926`（GKI 通道）；且 `remove_waiter` 是通用代码不受 vendor overlay 影响 —— 6.6.127 不可能比 6.6.118 **更**漏洞。

## R5 的两条新活线（此前从未进入路线表）

### 新线 A：`hdbd` —— 荣耀定制调试守护

`system_etc_init_hw_init.usb.rc:171-176`：

```
service hdbd /system/bin/hdbd --root_seclabel=u:r:su:s0
    class core
    user root
    socket hdbd stream 660 system system
    disabled
    seclabel u:r:adbd:s0
```

**`user root` + world-writable socket(660) + shell 域可能可 connect** —— 若它活着，这是**比属性注入更短的提权路径**（无需属性写入、无需 argv 注入）。同文件 `:26-32` 的 `adbd` 也有 `--root_seclabel=u:r:su:s0` + `user root`。

### 新线 B：`kcmdline_prop` 属性→argv 注入

**三个事实叠加**：

1. `:27078` `(allow shell kcmdline_prop (property_service (set)))` —— 显式 allow
2. `:25601` `(neverallow base_typeattr_880 kcmdline_prop (property_service (set)))` 但 `:32911` `base_typeattr_880 = (domain) − (init shell kcmdlinectrl)` ⇒ **shell 被显式排除在 neverallow 之外**（有意设计的放行）
3. `init_kcmdlinectrl.rc:22`：
   ```
   on property:kcmdline.binder=*
     exec -- /system/bin/kcmdlinectrl store binder ${kcmdline.binder:-c}
   ```
   init 的 `${}` 展开**不做 shell 分词/转义**，直接插入 argv

**唯一缺口 = 属性真名映射**（`property_contexts` 不在提取树中，4 个 raw 分区明文扫描 0 命中）。

### R5 同时推翻的三个前轮假设

| 前轮假设 | 裁决 |
|---|---|
| `hw_init.rc` 是「最高优先级补查项」 | ✗ 该文件**无可利用服务**（6 个 service 身份全收敛，`kcmdline` 命中 0）。注入面在 `init_kcmdlinectrl.rc` |
| `su` 域规则在 NUL 空洞里待查 | ✗ `su` 定义**完好**在 `:3979`（空洞在 class/classcommon 区）。真正问题是**它被 neverallow 封死** |
| `base_typeattr_880` 含 `kcmdline_prop` | ✗ 880 是 `(domain)−(init,shell,kcmdlinectrl)`；`kcmdline_prop` 是它的**约束对象** |

## R6：honor_binder 证伪（R2 的 B2 候选）

**判决：证伪。** 三项核心机制论断全部与设备侧反汇编不符。

| R2 论断 | R6 实测 |
|---|---|
| 「手工做页表翻译，绕过 uaccess 审计」 | **证伪**：唯一 BL → `memcpy`（`0xffffffc080552d90`）；全函数 **0 条 AT/TLBI/ldtr**；`[alloc+0x18]`/`[alloc+0x48]` 是 binder_alloc 自己的内核页数组（`page<<6` = `page_to_virt` 线性映射） |
| 「编入主 Image ⇒ SELinux 结构上不可能覆盖」 | **证伪**：主 Image 代码同样受 `genfscon` 约束。真实阻断来自无 ioctl 派发面 + shell 无授权，**与代码位置无关** |
| 「存在 ioctl 派发面」 | **证伪**：6 个 fops 的 `unlocked_ioctl`/`compat_ioctl`/`mmap`/`write`/`write_iter` **全 NULL** |

**阳性对照（决定性）**：真实 `copy_from_user` 链（`copy_from_user_nofault@0xffffffc0809e70e4`）的两个 BL 是 `__check_object_size` + `__arch_copy_from_user`（后者含 **7 AT + 12 TLBI + ldtr**）—— honor 版与该指纹**零交集**。

**唯一残留缺陷**：缺上游的 `check_buffer()`（丢 5 项边界保证），但调用点把长度 clamp 至 `[0x29, 0x10e]`、`buffer_offset` 硬编码 0 ⇒ **不可用户态触发**。

**附带纠错**：R2 记录魔数 `"TRUS"`，实测为 **`"TSYS"`**（`0x54 0x53 0x59 0x53`）。

## R7：opace6 移植价值裁决 ≈ 0

### 核心判断：opace6 不是本机的答案，而是一把「排除法」的尺

**它的成功路径 100% 经过 stageB/misc 桥**（`:5680-5799` 硬编码两阶段串行，`bridge_fd` 只能来自 `open_verified_bridge()`，两个失败分支无绕过）⇒ 「opace6 成功而本机卡 stageB W1」**不能**用 direct-probe 缺失解释。差异必然在**W1 命中概率 / 落点语义 / 时序参数**。

**它本身也不把 direct 当必需品**：三处 `STAGE8_TASK_DIRECT_FALLBACK` 会自动回落到全表扫描；第三方 `k80pro-miro` 文档独立标注这两项「✅ 可放弃」。

**「同基线兄弟」在符号层被证伪**：profile 记 110,445 符号，本机实测 **110,992**；且**每个数据符号差值非均匀**（`+0xc88`/`+0x1fb00`/`+0x1ddf8`/`-0x7ee0`/`-0x828ec8`）⇒ **不同 vendor 树 = 不同 build**。

> ⚠️ **反向禁令**：**禁止把 opace6 任何 `LINK_*` 搬进 f77.c**。f77.c 现有每个 `LINK_*` 都与本机 kallsyms 逐位吻合；opace6 CHANGELOG 自己就记录过「误用 dada（小米 15，**不同内核**）的 `bootidParent` → 致命」。

**移植优先级**：① `run_direct_probe_self_test`（唯一推荐，目的是**反向证伪**，预期 `stage=open errno=13`）② `tools/port_target.py` 参数化流水线（工程资产，防重演常量事故）③ 其余 8 个 direct 函数全部不做。

### dc15（`dc15_repro/`）未消化细节中最值钱的三条

1. **A/D 二元判据**（本项目最该继承的方法论）：对 owner 开火，nice 使 `p->prio ≠ waiter->tree.prio` ⇒ 闸门必不匹配 ⇒ 走链。**存活 ⇒ 链健康；panic ⇒ 链被 dance 弄坏。** 不需要 plant 就能测链健康度
2. **★ 仪器静默假阴性**（§3.4n）：exploit 的 tracefs KASLR 泄漏会**自己重设事件集**，把事先打开的 `sched_pi_setprio` 关掉 ⇒ `host_trace_*.log` 里 0 条而同窗口本应 10+ 条。**修好后同窗口抓到 648/394 条 ⇒ 前几轮「0 条」推论全部作废**
3. **★ route 线程的 syscall 覆写了自己的 waiter**（§3.4h 根因）：plant 之后、开火之前，route 线程自己发 syscall ⇒ **内核栈每线程复用，从栈顶重新往下用** ⇒ 闸门字被诊断日志覆盖。**教训：任何 plant 后的诊断都是攻击面**
