# 研究方法论

本文件记录该项目在长期实践中沉淀的**纪律性规则**。这些规则多数来自踩坑后的总结，
对同类内核漏洞研究具有普适参考价值。

---

## 一、上机操作纪律

| # | 规则 | 原因 |
|---|---|---|
| 1 | **一个 boot 只打一发** | 内核状态在触发后可能已进入不可信状态，多发叠加无法归因 |
| 2 | 崩溃判据**只看 `boot_id` + `history.log`** | 必须使用**独立透镜**验证；禁止用被测试程序自身的输出自证（循环自证） |
| 3 | 上机前**必验二进制**（md5 / 关键字符串） | 避免把错误版本的产物推到设备，浪费一次 boot |
| 4 | 出现「0 命中」**必须做阳性对照** | 0 命中往往是 harness 本身失效，而非漏洞不存在 |
| 5 | **禁止 `-static-pie`** | 在目标设备上直接 SIGSEGV；只做动态链接 |
| 6 | 不额外加 `-lpthread`（Android 下 pthread 在 libc 中）；跨线程标志用 `volatile` / `atomic` | 避免链接与可见性问题 |
| 7 | adb **串行**执行 | 并发 adb 会导致输出交错、时序失真 |
| 8 | 崩溃类实验**前台跑**，普通日志用 `nohup ... > file 2>&1 &` 事后 `cat`；跑前先 `rm -f` 旧日志 | 保证日志完整且不被上一轮污染 |

### 关于「崩溃判据」的独立性

这是最容易出错的一环。判定设备是否因本次触发而重启/崩溃时：

- ✅ 用 `boot_id`（每次启动唯一）+ 设备侧 `history.log` 这类**独立于被测程序**的证据源
- ❌ 不要用被测程序自己打印的「我成功了 / 我崩溃了」

否则一旦程序自身逻辑有误，会得到完全错误且自我强化的结论。

## 二、反汇编与偏移纪律（只信本机镜像）

### 核心原则

**任何偏移与机理结论，只信任从目标设备本机镜像中提取的证据。**

| 类别 | 处理方式 |
|---|---|
| 允许的证据源 | 本机提取的 `Image`（boot.img 解出）、配套反汇编脚本、可信公开源码树 |
| **禁止**的源 | 来源不明的「伪装源码树」（目录名看似官方但内容与目标 build 不符）、未经校验的 `btf_offsets*.txt` |
| 可信源码树 | 与目标 SoC/版本对应的公开内核树；读取时**必须按 commit 精确取文件**，不能依赖工作树（工作树可能未 checkout 到目标版本） |

### 证据分级标注（四级，不可混用）

在报告与代码注释中，每条结论都要标注其证据等级：

1. `[汇编已证]` —— 在本机镜像的反汇编中逐条指令确认
2. `[已实测]` —— 在真机上运行验证过
3. `[源码推断未验证]` —— 仅由源码阅读推出，尚未在本机镜像/真机确认
4. `[未验证]` —— 猜测值

> 实践中大量时间浪费在把「源码推断」当成「已证」使用。**混用等级是事故的主要来源**。

## 三、版本与补丁状态判定方法

判定「某个内核版本是否已修复某 CVE」时，采用**三环闭合**法，单一证据不足以定论：

1. **源码环**：对比未修复版本与已修复版本的源码差异（定位到具体函数与行号）
2. **常量环**：确认相关标志位/宏的取值（如 `SKBFL_SHARED_FRAG = BIT(1)`）
3. **本机汇编环**：在目标镜像的反汇编中确认该处指令形态（如 `cbz` → `ldrb` + `tbz #1`，指令数变化）

三环都对上才能下结论。同时需明确标注**该结论的边界**：
离线静态判决 ≠ 实机验证，应在报告中写明置信度与未验证的部分。

---

## 四、目标机保全

- 研究期间**冻结目标机的系统更新**。设备一旦跨版本升级，内核可能已被修复且 **BootLoader 锁定下无法回退**，导致该目标永久失效（本项目 PPG-AN00 即为实例）。
- 触发前记录当前 `boot_id` 与内核版本，便于事后归因。

---

## 五、工程纪律

- 改动后**必核 md5**，确保产物与预期一致。
- 上游参考代码**只读**，所有改动发生在自己的工作副本中，避免污染上游基线。
- 污染/废弃的分支**直接删除重建**，不做剥离式清理（剥离容易残留）。
- 声明版本稳定前，必须先验证**上一轮发现的 bug 已实际修复**（fix-then-test）。
